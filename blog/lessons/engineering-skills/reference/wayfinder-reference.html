wayfinder 速查参考

大型模糊工程的探路纪律：把路绘成 issue tracker 上的共享地图，逐票解决决策，直到通往目的地的路清晰。 系统学习请看第七课：使用 wayfinder 规划大型模糊项目。

来源：mattpocock/skills · wayfinder/SKILL.md（本地 ~/.agents/skills/wayfinder/SKILL.md）

一、什么时候用

  • 触发形状：想法太大——一个 agent session 装不下；太模糊——从这里到目的地的路还看不见。
  • 目的地的三种典型形态：要交接迭代的一份 spec、规划前要锁定的一个决策、一次就地完成的变更（如数据迁移）。
  • 不需要地图的信号：广度优先 grill 后没浮出任何雾——路已清晰、一个 session 装得下——停下来问用户想怎么走。
  • 该交接的信号：感到「别画了直接干」的冲动——说明已到地图边缘，交接给 to-spec → implement 主流程。

二、地图（map）结构

tracker 上带 wayfinder:map 标签的单个 issue；索引不是仓库——决策住在票里，地图只 gist + 链接；进行中的票不列在地图上，靠查询找。

区块内容
Destination到达终点长什么样，一两行；每个 session 选票前先对准它。
Notes领域、每个 session 该查阅的 skills、本工程的长期偏好；可在此声明「把施工带进地图」的例外。
Decisions so far索引：每张已关闭的票一行 gist + 链接；记录实际走过的路线。
Not yet specified范围内的雾：能感觉到但还钉不死的问题；随前沿推进毕业成票后从这里划掉。
Out of scope被排除在目的地之外的工作；永不毕业；越界的票关掉后在此留一行 gist + 原因 + 链接。

引用纪律：用名字不用编号——标题即链接，#42, #43 式的编号墙不可读。

三、决策票（decision ticket）

地图的 child issue，正文是一个 ## Question，大小适配单个 100K token session。

类型标签HITL / AFK干什么怎么解决
wayfinder:researchAFK挖决策等待的外部事实（文档、API、知识库）/research subagent，可并行，成果落 research/<name> 分支
wayfinder:prototypeHITL「该长什么样 / 该怎么表现」/prototype 做粗糙工件给大家 react，链接为资产
wayfinder:grillingHITL对话，默认类型总是配合 /grilling + /domain-modeling
wayfinder:taskHITL 或 AFK决策前必须先做的人工操作（开通服务、搬数据）唯一「做」的类型；资格是为决策解锁，答案记录产出的事实（凭证位置、URL、行数）
  • 认领（claim）：干活前把票 assign 给驱动地图的人；assignee 即认领标记，未 assign 的打开票 = 未认领。
  • 阻塞：用 tracker 原生依赖关系（让 frontier 在 tracker UI 上可见）；tracker 不支持才退回正文约定。
  • frontier = 打开 ∧ 未阻塞 ∧ 未认领的票。
  • HITL 票只能经真人实时交流解决——agent 自问自答即违规。答案不进正文，结案时以 resolution comment 记录；产物链接不进正文。

四、雾 / 票 / 范围之外 判别表

情况归宿
问题现在就能精确表述（哪怕被阻塞、暂时动不了）立票
能感觉到要来，但还表述不精确Not yet specified（雾；不要预切成票大小的片）
超出目的地范围Out of scope（永不毕业；已有票越界 → 关闭 + 留一行 gist/原因/链接）
已决定的Decisions so far（一行 gist + 链接）

五、两种调用模式

chart the map（绘制地图，一个 session 的工作量）

  1. 命名目的地：/grilling + /domain-modeling 钉死这张地图要找什么。
  2. 广度优先 grill 出全部开放决策与第一步；无雾则停，不需要地图。
  3. 建地图（Destination / Notes 填好，Decisions-so-far 空，雾进 Not yet specified）。
  4. 立现在能具体化的票 → 第二遍再连阻塞边（先有 id 才能互相引用）。
  5. 每张 research 票派一个 /research subagent 并行解决，票里留上下文指针。
  6. 停手——绘制地图的 session 一张票都不亲手解决。

work through the map（沿图推进）

  1. 加载地图（低分辨率视图，不读全部票正文）。
  2. 选票（用户点名 > 前沿第一张）→ 先认领再干活。
  3. 解决：按需 zoom 取相关/已关闭票正文；调用 Notes 点名的 skills；拿不准用 /grilling + /domain-modeling。
  4. 结案：resolution comment 写答案 → 关闭 issue → 地图 Decisions-so-far 追加上下文指针。
  5. 补新票（先建后连线）、毕业已清晰的雾（从 Not yet specified 划掉）、越界票判出范围、被推翻的票更新或删除。

六、铁律清单

  • plan, don't do：默认产出决策，不产出交付物。
  • 一个 session 最多解决一张票（research 票除外）。
  • 先认领（assign）再干活——预期别的 session 在并发编辑 tracker。
  • 地图是索引：一个决策只住在它的票里，地图不复述。
  • 引用用名字，不用裸编号。
  • Out of scope 永不毕业；重画目的地 = 全新工程，不是继续。
  • HITL 票的真人那一侧，agent 永远不得代答。

七、本地 markdown tracker 映射（无 issue tracker 时）

概念本地形态
地图.scratch/<effort>/map.md
票.scratch/<effort>/issues/NN-<slug>.md（从 01 编号；Type: 行记类型，Status: 行记 claimed/resolved）
阻塞票文件顶部 Blocked by: NN, NN 行；所列文件全部 resolved 即解锁
frontier扫 issues/ 目录：打开 ∧ 未阻塞 ∧ 未认领，编号最小者优先
认领Status: claimed，先保存再干活
结案答案追加在 ## Answer 下，Status: resolved，map.md 的 Decisions-so-far 追加 gist + 链接
