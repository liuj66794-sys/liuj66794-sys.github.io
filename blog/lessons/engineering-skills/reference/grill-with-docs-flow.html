grill-with-docs 流程参考

有代码库时，用 relentless interview（追问式访谈）把模糊想法磨成清晰计划，同时维护 CONTEXT.md 和 ADR。

来源：mattpocock/skills · grill-with-docs/SKILL.md（本地 ~/.agents/skills/grill-with-docs/SKILL.md）

一、什么时候用

用 /grill-with-docs不用 /grill-with-docs
有代码库，要设计新功能或改造现有模块 没有代码库，只是头脑风暴 → 用 /grill-me
需要把讨论中确定的术语、决策写成文档 对话已经结束，只需要整理成 spec → 用 /to-spec
想法还太模糊，直接写 spec 会漏掉关键假设 想法已经清楚，要拆任务 → 用 /to-tickets

二、grilling 的纪律

  1. 按 round（轮次）问完整个 frontier。frontier 是前提已确定、现在就能问的所有决策；每轮把它们编号后一次抛出，等用户答完再算下一轮。不再是一次只问一个。
  2. 问题格式固定：❓ **Q1** - **标题**:，另起一行 ➡️ 给出推荐答案；同一轮的多个问题之间用水平线 --- 分隔（2026-08-20 起）。决策是你的，但 agent 必须给建议。
  3. 沿着设计树的分支走，逐个解决决策之间的依赖关系。答案会重塑这棵树：已定的决策把 frontier 向外推，解锁依赖它们的后续问题。
  4. 事实查代码，决策问人。能靠探索代码库确认的事实，不要问用户——需要环境事实时派 sub-agent 去查，且不阻塞：只有它的下游问题等结果，其余 frontier 照问。
  5. 在达成 shared understanding（共同理解）之前不执行计划。frontier 清空（没有悬而未决的假设）并经用户确认后，访谈才算结束。

三、会产出什么文档

1. CONTEXT.md（领域词汇表）

只放项目特有的领域术语，不放通用编程概念。每个术语包含：定义 + 应避免的说法。 

# Order Context

A system for customers to place and track product orders.

## Language

**Order**:
A customer's request to purchase one or more items.
_Avoid_: Purchase, transaction

**Invoice**:
A request for payment sent to a customer after delivery.
_Avoid_: Bill, payment request

**Customer**:
A person or organization that places orders.
_Avoid_: Client, buyer, account

2. ADR（架构决策记录）

只有同时满足下面三点才写 ADR：

  • 难以逆转 —— 改主意成本很高
  • 没有上下文会令人惊讶 —— 未来读者会纳闷“为什么这样设计”
  • 真实权衡的结果 —— 考虑过替代方案并选了特定的一个
# 0001-event-sourced-orders

We decided to use an event-sourced write model for the Order context.

The alternative was a CRUD-style relational model, which would have been
simpler to implement but harder to audit and reason about for complex
lifecycle changes. Event sourcing gives us a complete history of every
order state change, which is critical for customer support and compliance.

四、典型流程

1

抛出想法：你描述一个模糊目标，例如“我想给订单系统加一个部分退款功能”。

2

Agent 开始 relentless interview（追问式访谈）：逐个问边界、术语、依赖。例如：“你说的‘退款’是退到原支付渠道，还是退到余额？”

3

实时维护 CONTEXT.md：一旦术语确定，立刻写入。比如把“refund”和“partial cancellation”区分开。

4

适时写 ADR：遇到难以逆转的决策时，提议记录。例如“退款状态机采用事件溯源”。

5

达成 shared understanding（共同理解）：双方对范围、术语、关键决策达成一致。此时可以进入 /to-spec 或 /implement。

五、常见陷阱

陷阱对策
Agent 一次问太多问题 提醒它：“一次只问一个。”
术语混用（“account”既指 Customer 又指 User） 要求写入 CONTEXT.md 并给出推荐说法。
每个小决定都写 ADR 只写同时满足“难逆转、会惊讶、有权衡”的决策。
还没想清楚就开始写代码 明确说“我们还在 grilling 阶段，不要 implement”。
记忆口诀

有代码库 → grill-with-docs；没代码库 → grill-me。
术语进 CONTEXT，难逆有权衡的决策进 ADR。
一次一问、给推荐、决策前不执行。
