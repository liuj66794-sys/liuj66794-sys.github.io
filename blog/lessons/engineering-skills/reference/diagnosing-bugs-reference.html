diagnosing-bugs 诊断循环速查

难 bug 与性能回退的六阶段诊断纪律：先建 red-capable 的紧反馈回路，再复现、假设、探测、修复、收尾。 系统学习请看第六课：使用 diagnosing-bugs 诊断难 bug。

来源：mattpocock/skills · diagnosing-bugs/SKILL.md（本地 ~/.agents/skills/diagnosing-bugs/SKILL.md）。 注意（2026-09-09）：本地副本已被第三方 claudekit 包覆盖成衍生版（不再是仓库原文），精读请用上面的 GitHub 链接，详见 RESOURCES.md 底部说明。

一、什么时候用

  • 用户说「diagnose」「debug this」，或报告某个东西 broken / throwing / failing / slow。
  • 触发信号：「这个 bug 我复现不了」「时好时坏」「更新之后变慢了」。
  • 探索代码库时先读 CONTEXT.md（如存在）和相关区域的 ADR。

二、六阶段及完成判据

阶段做什么完成判据
1. 建反馈回路 建一个 tight 且 red-capable 的 pass/fail 信号（见第三、四节）。这是灵魂，投入不成比例的精力。 能说出一条已跑过的命令（贴调用与输出），满足四判据。没有它，禁止进入 Phase 2。
2. 复现 + 最小化 跑回路看着它变红；一次砍一个变量，每砍一次重跑。 失败模式=用户描述的症状；可复现；每个剩余元素都是 load-bearing（再砍任何一个就变绿）。
3. 提假设 验证前先写 3–5 个排序假设，每个可证伪：「If X 是因，那么改 Y 会让 bug 消失/更严重」。 每个假设都带明确预测；排序列表已给用户看过（用户 AFK 则按自己的排序继续）。
4. 探测 每个探针对应一个预测，一次只改一个变量。调试器优先，其次边界打点；日志带 [DEBUG-xxxx] 前缀。 某个假设被证实或被排除。性能回退走分支：先测 baseline 再 bisect，先测量后修复。
5. 修复 + 回归测试 把最小复现变成正确 seam 上的失败测试 → 修复 → 变绿 → 用 Phase 1 回路复跑原始场景。 回归测试先红后绿；原始场景不再复现。没有正确 seam = 发现本身，记录并移交 /improve-codebase-architecture。
6. 收尾 + 复盘 过收尾清单（见第五节）；问「什么能阻止它再次发生」，架构答案移交 /improve-codebase-architecture。 清单逐条勾完；架构建议在修复落地之后提出。

三、十条建回路方法（按此顺序尝试）

#方法一句话
1失败测试在能触达 bug 的 seam 上写 unit / integration / e2e。
2curl / HTTP 脚本对运行中的 dev server 打请求断言响应。
3CLI + 快照fixture 输入，stdout 对已知正确快照 diff。
4headless 浏览器Playwright / Puppeteer 驱动 UI，断言 DOM / console / 网络。
5重放 trace真实请求 / 事件日志存盘，隔离重放进代码路径。
6一次性 harness最小子系统（mock 依赖），一次函数调用触发 bug 路径。
7property / fuzz「有时输出不对」：1000 个随机输入找失败模式。
8bisect 台架自动化「在状态 X 启动、检查、重复」，交给 git bisect run。
9差分对比同一输入跑新旧两版（或两种配置），diff 输出。
10HITL 脚本（兜底）必须人动手时，用 scripts/hitl-loop.template.sh 驱动人，回路保持结构化。

四、tight loop 四判据与收紧

  • red-capable（最核心）：驱动真实 bug 路径，断言用户的精确症状——能在这个 bug 上变红、修好后变绿，不是「跑完没报错」。
  • deterministic：每次运行同一判定；flaky bug 要求复现率足够高。
  • fast：秒级，不是分钟级。
  • agent-runnable：agent 可无人值守运行；人在回路只经由 HITL 脚本。

收紧三问：能更快吗？信号能更准吗（断言具体症状）？能更确定吗（固定时间、种子随机数、隔离文件系统、冻结网络）？

非确定性 bug：目标不是干净复现而是提高复现率——循环 100×、并行、加压、收窄时间窗；50% 可调试，1% 不行。

实在建不出回路：明确说出来，列出试过的方法，向用户要环境 / 抓取物（HAR、日志、coredump）/ 临时生产插桩许可——不要无回路硬进假设阶段。

五、脱敏规则（Redact，2026-08-06 新增）

  • 诊断中三条路径都可能把活 token 带进对话：粘贴调用及输出、构造 curl 循环、收集 artifact（日志、HAR 等）——先脱敏，再贴入。
  • token、cookie、密码、连接串一律替换为占位符；模型不需要被教会"什么是 secret"，见到可疑凭据就脱。
  • HITL 脚本里的 capture 会把值打印回终端，agent 读得到——涉及密钥时手动脱敏后再让它回显。
  • 背景：Snyk 审计 W007（HIGH）指出该 skill 原本存在凭据泄露风险，此节是修复。

六、收尾清单（Phase 6）

  • 原始（未最小化）场景复跑，bug 不再出现（用 Phase 1 回路）。
  • 回归测试通过（或 seam 缺失已记录）。
  • 所有 [DEBUG-...] 插桩已 grep 清除。
  • 一次性原型已删除（或移到明确标注的 debug 目录）。
  • commit / PR 信息写明哪个假设被证实是对的。
