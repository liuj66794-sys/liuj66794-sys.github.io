to-tickets 速查参考

把 spec/计划/对话拆成 tracer bullet（曳光弹）式的垂直切片 ticket，声明阻塞边，发布到 issue tracker（问题追踪系统）。

来源：mattpocock/skills · to-tickets/SKILL.md（本地 ~/.agents/skills/to-tickets/SKILL.md）

一、什么时候用

  • 已经有一份 spec（通常来自 /to-spec），需要拆成可实现的任务。
  • 有一个计划或一段足够清楚的对话，想变成 agent 可领取的 ticket。

二、前置条件

项目已运行 /setup-matt-pocock-skills：知道 issue tracker 在哪里、triage labels（分类标签）怎么叫。

三、垂直切片四条规则

规则说明
窄但完整 切穿所有层（schema、API、UI、测试），不是只切某一层的水平切片。
独立可验证 切片完成后可以单独演示或验证。
适配单个上下文窗口 一个全新 session 的 agent 能一次做完。
先预重构 prefactor（预重构）先行：让修改变容易，再做容易的修改。

四、阻塞边与 frontier

  • 每个 ticket 声明 Blocked by：哪些 ticket 必须先完成。
  • Blocked by: None = 可立即开始。
  • 按 frontier（前沿）推进：只做阻塞项全部完成的 ticket。
  • 纯线性链条 = 从头到尾；有分叉 = 分叉处可并行。

五、例外：wide refactor → expand–contract

wide refactor（大范围重构）：一个机械修改的 blast radius（爆炸半径）波及整个代码库， 无法用垂直切片承载。改用 expand–contract（扩张-收缩）：

1

Expand：新旧形态并存，什么都不破坏。

2

Migrate：按爆炸半径分批迁移（按包/按目录），每批一个 ticket，都被 expand 阻塞；旧形态还在，批间保持绿灯。

3

Contract：无调用者后删除旧形态，被所有迁移批次阻塞。

连批次都无法单独绿灯时：共享一个集成分支，共同阻塞最终的 integrate-and-verify ticket。

六、拆分流程

1

收集上下文：从对话出发；传入 spec 路径或 issue 编号则去读全文和评论。

2

探索代码库（可选）：用 CONTEXT.md 词汇，尊重 ADR，找 prefactor 机会。

3

起草垂直切片：标出每个 ticket 的阻塞边。

4

向你确认：粒度合适吗？阻塞边对吗？要合并或再拆吗？迭代到批准为止。

5

发布：本地 → .scratch/<feature-slug>/issues/<NN>-<slug>.md（按依赖顺序编号）；真实 tracker → 用原生 blocking/sub-issue 关系，打 ready-for-agent 标签。不要关闭或修改父 issue。

七、Ticket 模板

# <NN> — <Ticket 标题>

**What to build:** 用户视角的端到端行为（不是逐层实现清单）。

**Blocked by:** 阻塞它的 ticket 编号/标题，或 "None — can start immediately"。

**Status:** ready-for-agent

- [ ] 验收标准 1
- [ ] 验收标准 2

禁忌：不写具体文件路径和代码片段（很快过时）。 例外：原型产出的决策性代码（状态机、reducer、schema、类型形状）可内联，注明来自原型，只留决策密度高的部分。

八、发布之后

  • 用 /implement 按 frontier 逐个领取 ticket。
  • 每个 ticket 之间清空上下文（全新 session）。
