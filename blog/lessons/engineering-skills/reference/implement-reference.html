implement 速查参考

按 frontier 领取 ticket 完成实现：内部驱动 /tdd（red → green），收尾跑 /code-review（双轴审查），最后提交。 本页是查阅文档；系统学习请先看 第五课。

来源：mattpocock/skills · implement/SKILL.md（本地 ~/.agents/skills/implement/SKILL.md）

一、什么时候用

  • tracker 上有 agent-ready 的 ticket，且它的所有阻塞项已完成（在 frontier 上）。
  • 每个 ticket 用一个全新 session 实现，从 ticket 出发，不带前几阶段的上下文。
  • 也可以直接对一份 spec 使用（非 ticket 形态），规则相同。

二、前置条件

  • 已运行 /setup-matt-pocock-skills（issue tracker、triage labels、CONTEXT.md/ADR）。
  • 要领取的 ticket 位于 frontier 上，验收标准明确。

三、五条规则（SKILL.md 全文要点）

  1. 实现 spec/ticket 描述的工作——不多做，不少做。
  2. 尽可能用 /tdd，只在预先和用户确认的 seam 上写测试。
  3. 验证节奏：勤跑类型检查、勤跑单测试文件；完整测试套件只在最后跑一次。
  4. 完成后跑 /code-review。
  5. 提交到当前分支。

四、一个 ticket 的生命周期

步骤动作要点
1. 领取从 frontier 取 ticket读验收标准和 spec 上下文
2. 约定 seam确认公共接口和要测的 seam问：“公共接口是什么？测哪些 seam？”
3. red → green一个失败测试 → 最小实现 → 下一个一次一片；勤跑类型检查和单测试文件
4. 全量验证跑一次完整测试套件只在所有切片变绿后跑
5. 审查/code-review处理 Standards 与 Spec 两轴发现
6. 提交commit 到当前分支关闭 ticket，frontier 推进

五、tdd 要点

好测试的标准

  • 通过公共接口验证行为，不验证实现细节。
  • 读起来像规格说明，能在重构中幸存。
  • 探索代码库时先读 CONTEXT.md，尊重相关 ADR，测试命名用领域语言。

seam 铁律

  • 写任何测试前，把要测的 seam 写下来并和用户确认；没有任何测试写在未确认的 seam 上。
  • seam 通常继承自 spec（to-spec 模板要求声明），implement 阶段再确认一遍。

三个反模式

反模式表现识别信号
implementation-coupled mock 内部协作者、测私有方法、走旁路验证（如直接查库） 重构后测试挂，但行为没变
tautological 断言用和代码相同的方式重算期望值（expect(add(a,b)).toBe(a+b)） 构造上必然通过，永远不会失败
horizontal slicing 先写完全部测试，再写全部实现 测的是想象中的“形状”，不是用户行为

期望值必须来自独立真相来源：已知正确的字面量、手工算过的例子、spec。

循环三条规则

  1. Red before green：先失败测试，再刚好够通过的代码；不预判、不投机。
  2. One slice at a time：一个 seam、一个测试、一个最小实现。
  3. 重构不属于循环：留给 /code-review 驱动的审查阶段。

六、code-review 要点

双轴

轴审查什么来源
Standards 是否符合仓库成文规范 CODING_STANDARDS.md / CONTRIBUTING.md 等 + Fowler smell 基线（见下表）
Spec 是否忠实实现需求 原始 issue/PRD/spec；漏做、多做（scope creep）、做错都算发现
  • 两轴由并行 sub-agent 分别执行，汇总时不合并、不重排——防止一个轴掩盖另一个轴。
  • spec 查找顺序：commit message 里的 issue 引用 → 用户传入的路径 → docs/、specs/、.scratch/ 下匹配的文件 → 问用户。
  • diff 用三点语法 git diff <fixed-point>...HEAD（对 merge-base 比较）；先确认 fixed point 可解析且 diff 非空。

smell 基线的两条约束

  • 仓库规范优先：成文标准与基线冲突时，仓库赢。
  • 永远是判断题：smell 是启发式标签，不是硬性违规；工具已管的一律跳过。

12 种 Fowler 坏味道（是什么 → 怎么修）

Smell是什么怎么修
Mysterious Name名字不揭示用途或内容重命名；想不出诚实的名字说明设计含糊
Duplicated Code同一逻辑形状出现在多处提取共享形状，两处调用
Feature Envy方法对别的对象的数据兴趣超过自己的把方法移到它所羡慕的数据上
Data Clumps同样几个字段/参数总是一起出现捆成一个类型来传递
Primitive Obsession用原始类型代替本该独立的领域概念给概念一个小类型
Repeated Switches同一类型的 switch/if 级联反复出现用多态，或两处共享一张映射表
Shotgun Surgery一个逻辑修改被迫散落到许多文件把一起变的东西收进一个模块
Divergent Change一个模块因多种不相关原因被改拆分，让每个模块只为一个原因变化
Speculative Generality为 spec 没有的需求加了抽象、参数或钩子删掉，内联回去，等真实需求出现
Message Chains长长的 a.b().c().d() 导航链在第一个对象上用一个方法隐藏这段路径
Middle Man类或函数基本只在做转发砍掉，直接调真正的目标
Refused Bequest子类忽略或重写大部分继承来的东西放弃继承，改用组合

七、与其他 skill 的关系

  • 输入来自 /to-tickets（ticket + 阻塞边）；阻塞项未完成的 ticket 不能领。
  • /tdd、/code-review 都可以单独使用：只想测试先行地写个小功能就喊 /tdd；想审查任意分支/PR 就喊 /code-review 并给出 fixed point。
  • 审查发现的 Prefactor 需求或架构问题，可以回流成新的 ticket（回到 /to-tickets）。
