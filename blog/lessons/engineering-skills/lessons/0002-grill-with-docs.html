第二课：使用 grill-with-docs 打磨想法

上一课你记住了主流程：/grill-with-docs → /to-spec → /to-tickets → /implement。 这一课聚焦第一步：怎么用 /grill-with-docs 把一个模糊想法磨成可执行的 plan。

主源推荐（Primary Source）

本课内容基于官方 skill 定义，建议精读原文： grill-with-docs/SKILL.md （本地 ~/.agents/skills/grill-with-docs/SKILL.md）。

1. grill-with-docs 是什么？

它本质上是一场 relentless interview（追问式访谈）：agent 会一遍遍地追问你计划的每个分支， 直到你们对“要做什么、不做什么、关键术语是什么、关键决策是什么”达成 shared understanding（共同理解）。

和 /grill-me 的区别只在于：grill-with-docs 假设你有一个代码库， 因此它会把磨出来的术语写进 CONTEXT.md，把关键决策写进 docs/adr/。

何时选择哪个 grill
  • 有代码库 → /grill-with-docs
  • 没有代码库，只是纯头脑风暴 → /grill-me

2. grilling 的四条纪律

1

按轮（round）问完整个 frontier。frontier 是前提已确定、现在就能问的所有决策。每轮把它们编号后一次抛出——格式为 ❓ **Q1** - **标题**: 加 ➡️ 推荐答案，同一轮的问题之间用一条水平线（---）分隔（2026-08-20 起）——答完再算下一轮。（2026-07 起替代旧的"一次只问一个问题"。）

2

沿着设计树走。先解决会阻塞后续决策的决策，逐个分支推进。

3

每个问题给推荐答案。决策权在你，但 agent 应该提出倾向性建议供你确认或反驳。

4

事实查代码，决策问人。能靠代码库确认的东西（某个函数现在怎么工作）不要问用户。

3. 会产出什么文档？

CONTEXT.md —— 领域术语表

只收录这个项目特有的领域概念。比如“Order”“Refund”“Invoice”属于领域术语； “array”“Promise”“timeout”属于通用编程概念，不该出现。

每个术语一行定义，再加一个 _Avoid_ 列出应该避免的说法。例如： 

**Customer**:
A person or organization that places orders.
_Avoid_: Client, buyer, account

ADR —— 架构决策记录

只有同时满足三点才写：

  • 难以逆转：改主意代价大
  • 没有上下文会令人惊讶：未来读者会纳闷“为什么这样”
  • 真实权衡的结果：确实考虑过替代方案

例如：“订单写模型采用事件溯源”是 ADR； “我们用 2 空格缩进”不是。

4. 实战场景：部分退款功能

假设你对 agent 说：“我想给订单系统加一个部分退款功能。” 一场好的 grilling 可能会这样展开：

  1. “你说的‘退款’，是退到原支付渠道，还是退到平台余额？” → 决定术语和资金流。
  2. “部分退款后，订单状态是 refunded、partially-refunded，还是保持原状态？” → 写入 CONTEXT.md。
  3. “如果一笔订单分了 3 次退款，每次都要重新计算可退金额吗？” → 挖出状态机规则。
  4. “退款状态机采用事件溯源，方便审计，可以吗？” → 如果同意，写成 ADR。

5. 小测验：该写进哪里？

下面是在 grilling 中可能浮现的内容。请判断它应该进入 CONTEXT.md、ADR，还是都不写。

“我们的 `Order` 在部分退款后进入 `partially-refunded` 状态。”
“在这个项目里，‘Customer’指下单的人或组织，不要用 ‘account’ 来指代。”
“退款状态机采用事件溯源而不是直接更新数据库，因为我们需要完整审计轨迹。”
“我们用 TypeScript 5.3。”
【复习·第1课】主流程 idea → ship 的四步，正确顺序是？
【复习·第1课】/code-review 的“双轴审查”指的是哪两个轴？

6. 本课收获

  • /grill-with-docs = 有代码库时的 relentless interview（追问式访谈），产出 CONTEXT.md + ADR。
  • grilling 纪律：按轮问完 frontier、沿设计树走、给推荐答案、事实查代码。
  • CONTEXT.md 只放领域术语；ADR 只放“难逆转 + 会惊讶 + 有权衡”的决策。
  • 达成 shared understanding（共同理解）之前不进入实现。

7. 术语表

术语解释
relentless interview relent 追问式访谈。 agent 持续、细致地追问，直到把模糊想法磨清楚。
shared understanding 共同理解。双方对范围、术语、关键决策达成一致的状态。
CONTEXT.md 项目领域术语表。只收录这个项目特有的领域概念，每个术语包含定义和应避免的说法。
ADR 架构决策记录（Architecture Decision Record）。记录难以逆转、会令人惊讶、且经过权衡的架构决策。
domain model 领域模型。项目中核心业务概念及其关系的模型，通常体现在 CONTEXT.md 里。
ubiquitous language 通用语言。整个项目团队对领域术语的一致理解和使用。
event sourcing 事件溯源。用一系列事件记录系统状态变化，而不是直接保存当前状态。
refund state machine 退款状态机。描述退款从发起到完成的各个状态和转换规则。

8. 实战任务

选一个你正在维护的真实项目，挑一个你确实想做的功能，对它完整跑一次 /grill-with-docs，把磨出来的成果沉淀进项目文档：

  1. 在项目里对 agent 说“/grill-with-docs，我想做 XXX”，用一个真实功能开启访谈。
  2. 认真回答每一轮追问，遇到含糊处主动要求 agent 给推荐答案再确认。
  3. 访谈结束后，把磨出的领域术语写进该项目的 CONTEXT.md（含定义和 _Avoid_）。
  4. 检查过程中浮现的决策，把符合 ADR 三条件的写成 docs/adr/ 记录。
自检标准
  • CONTEXT.md 至少新增 2 个项目特有的领域术语，且不含通用编程概念。
  • 每个术语都带一行定义和 _Avoid_ 应避免说法。
  • 只有同时满足“难逆转 + 会令人惊讶 + 有权衡”的决策才写成了 ADR。
  • 访谈按轮进行：agent 每轮问完整个 frontier（❓编号 + 加粗标题 + ➡️推荐答案），事实性问题靠查代码而不是问你。

完成后回来告诉我结果（贴出产出或描述过程），我会给你反馈。

下一步

下一课通常是 /to-spec：把 grilling 的结果合成为一份 PRD。 或者你可以现在就找一个真实项目，对它说“/grill-with-docs，我想做 XXX”， 实际体验一次追问式访谈。学习中有任何不清楚的地方，随时直接问我——我是你的老师，可以针对任何一点展开讲。
