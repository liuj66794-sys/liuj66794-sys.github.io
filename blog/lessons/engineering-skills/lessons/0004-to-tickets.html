第四课：使用 to-tickets 拆分任务

上一课你用 /to-spec 把 grilling 的结果合成了一份 PRD。 这一课学习主线的下一步：怎么用 /to-tickets 把 spec 拆成一组 tracer bullet（曳光弹）式的 ticket，让每个 ticket 都能被 agent 独立领取实现。

主源推荐（Primary Source）

本课内容基于官方 skill 定义，建议精读原文： to-tickets/SKILL.md （本地 ~/.agents/skills/to-tickets/SKILL.md）。 建议完整读一遍原文，尤其是 wide refactor 段落的细节。

1. to-tickets 是什么？

/to-tickets 把一份 spec、计划或当前对话拆成一组 ticket。 每个 ticket 是一个 vertical slice（垂直切片），并声明自己的 blocking edges（阻塞边）——即哪些 ticket 必须先完成，它才能开始。

拆分确认后，ticket 会发布到项目的 issue tracker（问题追踪系统）， 并打上 ready-for-agent 标签，供后续 /implement 逐个领取。

2. 前置条件

和 /to-spec 一样，/to-tickets 假设项目已经运行过 /setup-matt-pocock-skills，即已配置好 issue tracker 和 triage labels（分类标签）。

3. 核心概念：垂直切片

拆分的第一原则是垂直切，而不是水平切。每个切片要满足四条规则：

  • 窄但完整：切穿所有层（schema、API、UI、测试），而不是只切某一层。
  • 独立可验证：一个切片完成后，可以单独演示或验证。
  • 适配单个上下文窗口：大小要能让一个全新 session 的 agent 一次做完。
  • 先预重构：如果现有代码让实现变难，先做一个 prefactor（预重构）ticket——“让修改变容易，再做容易的修改”。

垂直 vs 水平

水平切片（不要）垂直切片（要）
Ticket 1：写数据库 schema
Ticket 2：写 API
Ticket 3：写 UI		 Ticket 1：端到端打通“发起退款”最小流程
Ticket 2：端到端打通“查看退款状态”
任何一层完成都无法演示，最后才能验收。 每个 ticket 完成即有一个可用的小功能。

4. 阻塞边与 frontier

每个 ticket 声明自己的 Blocked by：哪些 ticket 必须完成后它才能开始。 没有任何阻塞的 ticket 可以立即开始。

实现时按 frontier（前沿）推进：任何时刻，只做“所有阻塞项都已完成”的 ticket。 如果整个链条是纯线性的，就是从头到尾顺序做；如果有分叉，分叉处的 ticket 可以并行。

5. 例外：大范围重构用 expand–contract

wide refactor（大范围重构）是垂直切片的例外： 一个机械性修改（比如重命名一个字段、改一个共享类型），其 blast radius（爆炸半径）波及整个代码库，一次改动会让上千个调用点同时报错， 任何垂直切片都无法保持绿灯。这时不要硬塞进曳光弹，改用 expand–contract（扩张-收缩）：

1

Expand（扩张）：新形态和旧形态并存，先加新的，不动旧的，什么都不破坏。

2

Migrate（迁移）：按爆炸半径分批迁移调用点（按包、按目录），每批一个 ticket， 都被 expand 阻塞。旧形态还在，所以每批之间 CI 保持绿灯。

3

Contract（收缩）：确认没有调用者后删除旧形态，这个 ticket 被所有迁移批次阻塞。

如果连迁移批次都无法单独保持绿灯，可以让它们共享一个集成分支， 共同阻塞一个最终的 integrate-and-verify ticket——绿灯只在那里承诺。

6. 拆分流程

1

收集上下文：从当前对话出发；如果你传入 spec 路径或 issue 编号，agent 会去读全文和评论。

2

探索代码库（可选）：ticket 标题和描述要用 CONTEXT.md 的领域词汇，并尊重相关 ADR；顺手找 prefactor 机会。

3

起草垂直切片：按上面的规则拆，并标出每个 ticket 的阻塞边。

4

向你确认：agent 会列出编号清单（标题 / Blocked by / 交付什么），问你三件事——粒度合适吗？阻塞边对吗？要合并或再拆吗？迭代到你批准为止。

5

发布：本地模式写到 .scratch/<feature-slug>/issues/<NN>-<slug>.md（按依赖顺序编号，阻塞者在前）； 真实 tracker 模式按平台原生的 blocking/sub-issue 关系建 issue，打 ready-for-agent 标签。

7. Ticket 模板与禁忌

每个 ticket 包含：

  • What to build：用户视角的端到端行为，不是逐层实现清单。
  • Blocked by：阻塞它的 ticket 编号/标题，或 “None — can start immediately”。
  • Acceptance criteria：验收标准清单。
  • Status：ready-for-agent。

禁忌：和 spec 一样，不写具体文件路径和代码片段——它们很快会过时。 唯一例外是原型产出的决策性代码（状态机、reducer、schema、类型形状），可以内联并注明来自原型。

8. 小例子：部分退款功能的拆分

接着上一课的“部分退款” spec，/to-tickets 可能产出这样的拆分：

#TicketBlocked by交付什么
01 Refund 模块骨架与退款状态机 None 通过公共接口能创建退款并推进状态
02 端到端发起部分退款 01 顾客能对订单部分商品退款，钱退回原支付渠道
03 客服后台发起退款入口 02 客服能代顾客发起部分退款
04 订单页展示退款状态 02 顾客能在订单页看到退款进度

注意 frontier 的形状：01 完成后 02 解锁；02 完成后，03 和 04 可以并行， 因为它们互不阻塞。每个 ticket 都用 /implement 在全新上下文中单独完成。

10. 本课收获

  • /to-tickets 把 spec 拆成垂直切片 ticket，每个声明阻塞边。
  • 垂直切片：窄但切穿所有层、独立可验证、适配单个上下文窗口。
  • 按 frontier 推进：只做阻塞项全部完成的 ticket；分叉处可并行。
  • 大范围重构是例外：用 expand–contract 分阶段，保持批间绿灯。
  • ticket 写用户视角行为 + 验收标准，不写文件路径和代码片段。
  • 发布后打 ready-for-agent 标签，由 /implement 逐个领取。

11. 术语表

术语解释
tracer bullet 曳光弹。先做一颗打穿全系统的最小子弹验证方向，再逐步加厚，而不是分层逐层建。
vertical slice 垂直切片。一个窄但完整的功能切片，切穿 schema、API、UI、测试所有层。
blocking edge 阻塞边。ticket 之间的依赖关系：A 被 B 阻塞 = B 完成后 A 才能开始。
frontier 前沿。当前所有阻塞项均已完成的 ticket 集合，即此刻可以开工的部分。
wide refactor 大范围重构。一个机械性修改，其影响波及整个代码库，无法用垂直切片承载。
blast radius 爆炸半径。一次修改会波及多少调用点；半径越大，越要分批迁移。
expand–contract 扩张-收缩。先让新旧形态并存，再分批迁移，最后删除旧形态的重构策略。
prefactor 预重构。在实现功能前先做的简化重构——“让修改变容易，再做容易的修改”。
acceptance criteria 验收标准。判断 ticket 是否完成的可勾选条件清单。

12. 实战任务

别只看不练。打开你自己的真实项目，把上一课用 /to-spec 产出的那份 spec 交给 /to-tickets，亲手完成一次拆分：

  1. 在真实项目里调用 /to-tickets，传入上一课产出的 spec（路径或 issue 编号）。
  2. 和 agent 一起把 spec 拆成一组 tracer-bullet 式的垂直切片 ticket，每个 ticket 都是端到端可验证的小功能。
  3. 为每个 ticket 显式声明 Blocked by（阻塞边），确认没有阻塞的 ticket 可以立即开工。
  4. 回答 agent 的确认三问：粒度合适吗？阻塞边对吗？要合并或再拆吗？迭代到你批准为止。
  5. 确认发布结果：本地模式检查 .scratch/ 下的 ticket 文件，或 tracker 模式检查 issue 与 ready-for-agent 标签。
自检标准
  • 每个 ticket 都是垂直切片：切穿 schema、API、UI、测试，完成即可单独演示。
  • 没有任何 ticket 是“只写某一层”的水平切片。
  • 每个 ticket 的阻塞边都明确写出（或写明 “None — can start immediately”）。
  • 第一个 ticket 不依赖任何东西，现在就能交给 /implement 立刻开工。

完成后回来告诉我结果（贴出产出或描述过程），我会给你反馈。
