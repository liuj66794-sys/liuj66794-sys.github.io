第三课：使用 to-spec 生成 PRD

约 2412 字大约 8 分钟

2026-07-26

这是本课阅读版。打开互动课程（在新窗口打开），即可在同一页阅读与练习。

上一课你用 /grill-with-docs 把模糊想法磨清楚了。这一课学习下一步： 怎么用 /to-spec 把讨论结果合成为一份正式的 PRD/spec。

主源推荐（Primary Source）

本课内容基于官方 skill 定义，建议精读原文： to-spec/SKILL.md （本地 ~/.agents/skills/to-spec/SKILL.md）。

1. to-spec 是什么？

/to-spec 会把当前对话和代码库理解合成为一份 PRD（Product Requirements Document，产品需求文档）。 它不再 interview，只是把已经确定的东西写成结构化文档。

写完后，spec 会发布到项目的 issue tracker（问题追踪系统），并打上 ready-for-agent 标签， 供后续 /to-tickets 拆分。

2. 前置条件

/to-spec 假设项目已经运行过 /setup-matt-pocock-skills。 如果没有，agent 会提示你先配置 issue tracker 和 triage labels（分类标签）。

3. Spec 模板

一个完整的 spec 包含以下部分：

Problem Statement（问题陈述）

用户视角的问题描述。不要写技术细节，只写“用户遇到了什么麻烦”。

Solution（解决方案）

用户视角的解决方案。描述新功能怎么解决上面的问题。

User Stories（用户故事）

一个非常长的编号列表，覆盖功能的所有方面。 格式：As an <actor>, I want a <feature>, so that <benefit>

Implementation Decisions（实现决策）

已经确定的技术决策：

  • 要构建或修改的模块
  • 模块的接口
  • 架构决策
  • Schema 变更
  • API 契约
  • 具体交互

注意：不要写具体文件路径或代码片段（原型产出的决策性代码除外）。

Testing Decisions（测试决策）

测试计划：

  • 好测试的标准（只测外部行为，不测实现细节）
  • 哪些模块会被测试
  • 代码库里已有的类似测试作为参考

Out of Scope（范围之外）

明确排除的内容。写清楚不做的事情和做同样重要。

Further Notes（备注）

其他备注。

4. Seams：测试边界

在写 spec 之前，agent 会先和你确认测试接口（seams）。 一个好的 spec 应该说明：

  • 哪些现有 seams 可以复用
  • 需要新增哪些 seams
  • 测试应该打在哪一层

理想情况是整个功能通过一个公共接口就能测试，seam 数量越少越好。

5. 关键规则

规则原因
不 interview，只合成对话已经清楚，再追问是浪费时间。
用 CONTEXT.md 的词汇保持术语一致，避免“account” vs “Customer”的混乱。
不写文件路径和代码片段文件路径和代码很快会过时，spec 会失真。
User Stories 要长覆盖所有方面，不是象征性地列几条。
明确 Out of Scope防止范围蔓延，给后续 /to-tickets 划定边界。

6. 小例子：部分退款功能

假设 grilling 已经确认了这些：

  • 术语：Refund、Partial Refund、Order、Customer
  • 决策：退款状态机采用事件溯源（已写 ADR）
  • 决策：退款到原支付渠道，不是平台余额
  • 决策：部分退款后订单进入 partially-refunded 状态
  • 不做：退款到余额、撤销退款

那么 /to-spec 产出的 spec 会大致是：

<code>## Problem Statement

顾客收到有瑕疵的商品时，目前只能整单退款或完全不退，无法只退还部分金额。

## Solution

支持部分退款。顾客或客服可以对订单中的部分商品发起退款，退款金额按商品价格比例计算。

## User Stories

1. As a customer, I want to request a refund for specific items in my order, so that I only pay for the items I keep.
2. As a customer, I want to see the refund status of my order, so that I know when my money will be returned.
3. As a support agent, I want to issue a partial refund on behalf of a customer, so that I can resolve complaints without returning the whole order.
4. As a customer, I want the refund to go back to my original payment method, so that I don't have to manage a separate balance.

## Implementation Decisions

- 新增一个 `Refund` 模块，只暴露很小的公共接口。
- 引入 `partially-refunded` 订单状态。
- 退款状态机采用事件溯源（见 ADR-0001）。
- 退款通过原支付渠道处理。
- 退款金额按商品价格比例计算。

## Testing Decisions

- 通过公共的 `Refund` 接口测试，而不是内部状态机事件。
- 复用现有的 order service 测试 seams。
- 参考代码库里已有的支付集成测试。

## Out of Scope

- 退款到平台余额。
- 发起退款后撤销或取消退款。
- 运费退款。

## Further Notes

退款状态机的原型代码片段已内联到 ADR-0001 中。</code>

7. 小测验：该放进哪个部分？

“顾客收到有瑕疵的商品时，目前只能整单退款或完全不退。”

  • A. User Stories
  • B. Problem Statement
  • C. Implementation Decisions
  • D. Out of Scope
点开核对答案

答案：B（Problem Statement） —— 正确。Problem Statement 描述用户视角的问题。

“As a customer, I want the refund to go back to my original payment method, so that I don't have to manage a separate balance.”

  • A. User Stories
  • B. Solution
  • C. Testing Decisions
  • D. Out of Scope
点开核对答案

答案：A（User Stories） —— 正确。这是标准的 User Story 格式。

“退款状态机采用事件溯源。”

  • A. User Stories
  • B. Problem Statement
  • C. Implementation Decisions
  • D. Out of Scope
点开核对答案

答案：C（Implementation Decisions） —— 正确。这是技术实现决策，应写入 Implementation Decisions。

“不支持退款到平台余额。”

  • A. User Stories
  • B. Solution
  • C. Testing Decisions
  • D. Out of Scope
点开核对答案

答案：D（Out of Scope） —— 正确。明确排除的功能应写入 Out of Scope。

【复习·第1课】为什么 grill → to-spec → to-tickets 要尽量放在同一个未中断的 context window 里完成？

  • A. 因为新开的 context 无法读取 CONTEXT.md
  • B. 保持讨论细节完整，避免上下文污染
  • C. 因为 slash 命令只能按固定顺序调用
  • D. 因为 ticket 拆分依赖模型缓存的命中
点开核对答案

答案：B（保持讨论细节完整，避免上下文污染） —— 正确。打磨出的细节都在对话里，换 context 会丢失或被污染，所以前三步要在同一窗口走完。

【复习·第2课】grilling 之后，下面哪条内容应该写进 ADR？

  • A. 订单写模型采用事件溯源，方便审计
  • B. 团队约定代码统一使用两空格缩进
  • C. 项目的后端使用 TypeScript 5 开发
  • D. 在测试里用工厂函数构造测试数据
点开核对答案

答案：A（订单写模型采用事件溯源，方便审计） —— 正确。事件溯源难以逆转、没有上下文会令人惊讶、且经过权衡，符合 ADR 的三个标准。

8. 本课收获

  • /to-spec 把 grilling 结果合成为 PRD，不 interview。
  • 模板包含：Problem Statement、Solution、User Stories、Implementation Decisions、Testing Decisions、Out of Scope、Further Notes。
  • User Stories 要长，Out of Scope 要明。
  • 不写文件路径和代码片段。
  • 写完后发布到 issue tracker，打 ready-for-agent 标签。

9. 术语表

术语解释
PRDProduct Requirements Document，产品需求文档。描述要构建什么、为什么、怎么验收。
issue tracker问题追踪系统。比如 GitHub Issues、Linear、Jira 等，用于管理 ticket。
triage labels分类标签。用于标记 issue 的状态，如 needs-triage、ready-for-agent 等。
seam测试边界/接缝。可以观察行为而不触及内部实现的公共接口。
user story用户故事。以用户视角描述一个功能需求，格式为“As an actor, I want a feature, so that benefit”。
scope creep范围蔓延。项目范围在无意识中不断扩大，导致难以交付。
event sourcing事件溯源。用一系列事件记录系统状态变化，而不是直接保存当前状态。
prototype原型。用来验证设计问题的一次性代码，得到答案后可以删除或归档。

10. 实战任务

接续上一课的实战：拿你在真实项目里用 /grill-with-docs 磨清楚的那个想法， 在自己的项目里完成下面的任务。

  1. 打开上一课 grilling 的那个项目，确认 CONTEXT.md 和 docs/adr/ 里的产出还在。
  2. 对 agent 说“/to-spec”，让它把 grilling 的结果合成为一份 spec。
  3. 通读生成的 spec：对照本课的模板，检查每个部分是否齐全、术语是否与 CONTEXT.md 一致。
  4. 让 agent 把 spec 发布到项目的 issue tracker，并打上 ready-for-agent 标签。
  5. 如果发现 spec 里有遗漏或跑题，直接在对话里指出，让 agent 修订后重新发布。

自检标准

  • spec 中的领域术语全部来自 CONTEXT.md，没有出现“account”vs“Customer”这类混用。
  • User Stories 是可验收的编号列表，覆盖功能的各个方面，而不是象征性地列两三条。
  • Out of Scope 明确列出了不做的内容。
  • 全文没有 interview 式的开放问题、文件路径或代码片段——只有已经确定的决策。

完成后回来告诉我结果（贴出产出或描述过程），我会给你反馈。
