规范 0001 · 学习工作区移动端适配（手机版）

约 1876 字大约 6 分钟

2026-08-21

状态：ready-for-agent（本地发布——本工作区无 issue tracker，spec 以文件形式落在 specs/） 前置：docs/adr/0001-mobile-single-file-inline.md（手机版采用单文件内联分发）

Problem Statement

用户想在手机上复习学习工作区的课程内容。真实使用路径是：电脑微信文件助手把 HTML 文件发到手机 → 手机 Chrome 打开。这条路径只能传输单个文件，assets/ 目录过不去，页面引用的样式和脚本全部丢失，渲染退化为纯文本——桌面端精心设计的排印在手机上完全不存在，复习体验非常难受。

Solution

桌面源文件保持不变。提供一个可重复运行的构建脚本，把每个 HTML 页面引用的样式与脚本全部内联，生成一组自给自足的单文件副本（手机版）。用户想复习哪一课，就用微信文件助手把对应的那一个文件传到手机，打开即是完整排印。手机版不保证页面间导航可用，使用方式是"一次传一课"。

User Stories

  1. 作为手机端的复习者，我想在微信文件助手里把一个课程 HTML 传到手机后能直接打开阅读，以便不需要电脑和网络服务器就能复习。
  2. 作为手机端的复习者，我想打开的单文件渲染出和桌面端一致的样式（字体、发线分节、目录、测验组件），以便获得正常的阅读体验而不是纯文本。
  3. 作为手机端的复习者，我想课程末尾的小测验在手机上可点可选、能出即时反馈，以便完成完整的学习闭环。
  4. 作为手机端的复习者，我想在手机有网络时照常加载 Google Fonts 字体，无网时回退系统字体也能阅读，以便不被网络条件卡住。
  5. 作为内容维护者，我想桌面源文件和共享样式一个字都不被这次适配改动，以便桌面端阅读体验保持现状。
  6. 作为内容维护者，我想手机版是构建产物而不是手工维护的副本，以便我不需要记住"改内容时要同步改两处"。
  7. 作为内容维护者，我想改完任何课程内容后跑一次命令就能重新生成全部手机版文件，以便手机版永远和源文件同步。
  8. 作为内容维护者，我想重新生成是全量幂等的——跑多次结果一致、手工改过产物也会被覆盖回正确状态，以便产物永远可信。
  9. 作为内容维护者，我想新增一个 HTML 页面后不需要改构建脚本就能被纳入生成范围，以便工作区持续生长时适配不增加额外负担。
  10. 作为桌面端的使用者，我想在桌面浏览器打开手机版整组文件时，"返回学习地图"等站内链接仍能正确跳转，以便手机版文件在桌面上也是自洽可用的一套副本。
  11. 作为手机端的复习者，我接受手机上点站内链接打不开（文件传输不保持目录结构），以便换取"一次传一课"的零门槛分发。
  12. 作为验收者，我想有自动化测试守住"产物中不存在任何外部资源引用"这条底线，以便以后改脚本或改样式时不会悄悄把手机版改坏。

Implementation Decisions

  • 唯一新增模块：构建脚本（Node，零第三方依赖，CommonJS 或 ESM 均可，用 Node 24 内置 API）。职责：扫描工作区中全部内容 HTML（导航页、课程、参考），对每个文件执行内联转换，按原目录结构镜像输出到 mobile/ 目录，文件名不变。
  • 内联转换规则：
    • <link rel="stylesheet" href="…"> 替换为内联 <style>，内容为被引用的 CSS 全文。
    • CSS 中的本地 @import（如样式入口引用设计令牌文件）递归展开为被引用文件的内容；远程 @import（Google Fonts）原样保留并提升到所在 <style> 块的顶部，保证浏览器仍认它为合法 @import。
    • <script src="…assets/…"> 替换为内联 <script>，内容为被引用的 JS 全文；defer 属性随标签一并消失（页内目录脚本自带 DOM ready 守卫，行为不受影响）。
    • 页面中已存在的内联 <script>（如测验答案数据）原样保留。
  • 页内目录根路径补丁：目录组件（toc）原本从自身 script src 推导工作区根路径，内联后该推导失效。构建脚本在内联时按页面所在层级改写推导结果：根目录页面为 ./，子目录页面为 ../。这是生成物层面的补丁，源文件中的目录组件不做任何改动。
  • mobile/ 是生成物：约定任何内容修改只改源文件，然后重跑脚本；手工编辑产物会在下次生成时被覆盖。此约束已记录在 ADR 0001 的 Consequences 中。
  • 不新增任何移动端样式：本次严格限定为"让手机渲染出与桌面一致的样式"。窄屏体验问题待真机观察后另行处理。

Testing Decisions

  • 什么是好测试：只测外部行为——以 CLI 方式运行构建脚本，断言生成文件的内容特征；不 import 脚本内部函数，不断言中间数据结构。
  • 测试的模块：唯一的模块即构建脚本本身，seam 为其 CLI 边界（运行命令 → 检查产物）。
  • 核心断言（针对产物）：
    • 不存在 <link rel="stylesheet">；不存在指向 assets 的 <script src=…>；不存在本地 @import；远程字体 @import 保留且位于样式块顶部。
    • 测验脚本与页内目录脚本的内容确实出现在产物中。
    • 子目录页面的目录组件根路径被补丁为 ../，根目录页面为 ./。
    • 产物目录结构镜像源结构，13 个 HTML 一个不少。
  • 测试框架：Node 24 内置 node:test + node:assert，零依赖。可用临时目录构造小型 fixture（含 link/script/@import 的迷你 HTML 与 CSS/JS）跑转换，再对真实工作区跑一次冒烟。
  • Prior art：工作区此前无任何测试，这是第一篇。
  • Playwright 手机视口截图属于人工验收手段，不自动化——渲染效果靠眼看。

Out of Scope

  • 任何新的移动端专属样式（点击区域、字号、折叠目录等）——等真机发现真实痛点后另行处理。
  • 手机上页面间导航可用的任何方案（巨型合并文件、局域网服务器、公网部署）——ADR 0001 已明确拒绝。
  • 把工作区变成 git 仓库、接入 issue tracker、配置 CI。
  • 桌面端的任何改动。
  • Markdown 文件（学习记录等）的移动端阅读——手机浏览器本就能渲染纯文本 Markdown，不属于本次问题。

Further Notes

  • 术语遵循 CONTEXT.md：手机版、主源、速查表等；决策背景见 ADR 0001。
  • 传输路径仍为人工操作（微信文件助手），本 spec 不优化传输本身。
  • 后续若接入 /to-tickets，建议拆分为：① 构建脚本核心内联逻辑；② toc 根路径补丁；③ 测试；④ 全量生成 + 人工验收。
